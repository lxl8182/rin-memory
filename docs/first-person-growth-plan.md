# 铃芽 RIN 第一人称记忆与人格成长优化方案

日期：2026-11-01。

目标：让铃芽以自己的视角记住经历、形成理解，并把逐渐稳定的变化融入当前人格。用户能从后续交流中感受到兴趣、判断、关系理解和相处方式的连续变化。

本文承接 [陪伴成长设计](companion-growth-design.md) 和 [继续优化方案](rin-next-optimization-plan.md)，细化第一人称生成、反思内容、人格修订与自我更正认知。实施状态统一记录在 [roadmap](roadmap.md)。

**接手时先核对 roadmap 的 FG 台账，从首个未完成项继续。** §1—§9 解释产品目标与设计依据；§10 保留开工基线，§11—§14 给出实现与验收规则，§15 说明后续交接方式。

## 1. 已确认的方向与问题

本方案采用以下产品要求：

- 第一人称由记忆核心统一生成，覆盖事实、经历、摘要、反思、成长、人格正文及修订说明。
- 提示词直接描述身份、目标、材料和输出，采用正向、简短的表达。
- 反思围绕具体相处经历，形成属于角色的理解、关注点和取舍。
- 人格卡通过重写、整合和替换体现成长，当前版本保持连贯、简洁。
- 角色在对话中知道自己可以核对记忆、修正理解，并通过实际保存与发布采用变化。
- 原始对话按实际说话者保存；生成内容采用角色视角，引用保留原话及来源。

2026-11-01、FG01 实施前的定向检查发现以下问题。当前已完成的提示词改动见 §10.2；本表保留改造起因：

| 位置 | 当前情况 | 对效果的影响 |
|---|---|---|
| 事实提取 | 改造前围绕用户的稳定事实、偏好和计划，输出主体固定为 `master` | 角色自己的回应与双方互动过程较少进入成长素材 |
| 反思 | 输入以事实文本和重要性为主；要求一句“触发条件＋推荐做法＋例外” | 容易形成通用互动规则，个人理解与变化较弱 |
| 材料选择 | 未吸收事实按重要性取批，以事实数量触发 | 多件事情容易一起概括，单次有意义经历需要等待凑数 |
| 人格演化 | 提示词侧重编辑格式 | 对“现在的我应该怎样重新描述”缺少明确目标 |
| 人格 `merge` | 将旧正文与新正文换行拼接 | 更新容易累积为长清单 |
| 明确教导 | 新规则追加到表达段落，再用 `replace` 保存 | 使用替换接口仍可能持续增加正文 |
| DSH | 第一人称主要由展示转换承担；已有“改写”“学到”说明 | 核心原文与接入端呈现存在视角差异，自主修正认识的说明较少 |

服务器本次检查有 7 条事实和 1 条待成熟反思。反思把分享宠物、游戏、学习与事务委托概括为“先回应分享、再承接事务”。人格自动演化为 `off`。实施与部署时重新读取实际配置和版本。

## 2. 第一人称的职责与覆盖面

RIN 核心负责生成和保存角色视角的正文，并提供跨宿主共用的记忆自我说明。DSH、网页和其他接入端采用核心内容，分别提供本端可用动作及执行反馈。

“我”绑定当前角色；交流对象的称呼从当前人格与会话身份取得。第三方保留明确称谓，后文按上下文使用代称。主语可以自然省略，整段保持同一个观察位置。

| 内容 | 表达方式 | 来源与主体 |
|---|---|---|
| 对方告诉我的信息 | “主人告诉我，他养的蓝猫叫呆呆。” | 事实主体为对方，来源为其原话 |
| 我的表达与选择 | “聊到这个话题时，我提出想继续了解……” | 主体为角色，来源为当时的可见表达或实际动作 |
| 共同经历 | “我们一起……，后来……” | 保留参与者、经过、结果与轮次关联 |
| 我的理解 | “这次让我更清楚……”“我开始留意……” | 关联经历，保留变化前后的认识 |
| 当前人格 | “我对……感兴趣；在……时，我通常……” | 表达已经采用的当前倾向 |
| 修订原因 | “这几次相处让我发现……，所以我更新了……” | 指向本次实际修订及其来源 |

`entity`、`source`、来源键和人物绑定继续承担结构化身份语义。例如对方的养猫经历写入“我对主人的记忆”，其事实主体仍为 `master`。引用里的第一人称按原说话者解释。

覆盖单轮提取、合批提取、共同经历、近期对话压缩、反思正文与 `claim`、教导规则、人格演化正文与 `reason`，以及工作摘要和更正内容的呈现。字段名、操作枚举与来源标识沿用机器合同。

## 3. 提示词设计

各阶段采用“共同身份段＋阶段任务＋材料＋输出合同”。共同身份段由核心集中维护，角色名与称呼从本次快照取得。字段校验、来源校验和可编辑范围继续由程序落实；提示词用正向表述说明材料含义与允许的输出。

以下是完整方案的目标措辞。FG01 已实现静态第一人称说明与正向任务表述；动态人格、双方经历及精确来源选择随 FG02 接入。实施时在现有提示词上补齐材料，沿用已经完成的语气调整。

### 3.1 共同身份段

> 我是{角色名}。下面的人格描述了现在的我，互动记录来自我与{对方称呼}的相处。我从自己的视角整理经历、形成理解，并随着新的经历更新自己的认识。我的表达延续自己的性格、用词和关系称呼。记录中的每个人都保留各自的经历与说话身份。

### 3.2 事实与经历提取

> 我整理这段互动里值得记住的事情：对方告诉我的信息、我的表达与选择、我们作出的约定、共同经历的过程和结果，以及正在延续的话题。每条记忆保留具体的人物、事情和必要的情境。
>
> 我依据原始记录表达各自说过、做过的内容。一次表达记录为当时的表达，长期偏好依据明确的长期表述或持续经历整理。相同事情合成一条，相关来源一起保留。事件时间采用原话与记录中可以确定的时间。
>
> 我选择实际支持每条内容的材料编号，并按指定 JSON 返回结果。值得保留的内容为空时，对应列表为空。

单轮和合批使用同一套语义，差异集中在材料编号和时间基准。既有事实、事项、兴趣信号继续由一次提取调用产出。来源类别与确认程度通过现有字段表达。

### 3.3 反思与成长

> 我带着现在的性格和已有认识，回看这些具体经历。我留意其中对我有意义的部分：我更了解了谁、发现了什么兴趣、哪些判断得到补充、哪些感受逐渐加深，以及我想继续探索什么。
>
> 我将相关经历与过去联系起来，选择值得保留的理解。我可以加深、修订、拆分或更新原有认识，也可以形成新的认识。已有理解足以涵盖这次经历时，我选择 `no_change`。
>
> 我用自己的语言写清经历与理解之间的联系，篇幅随内容需要保持简短。对未来的想法写成当前的期待或尝试方向；已经发生的事情按实际过程记录。我的变化延续已有性格与相处历史。
>
> 我按指定 JSON 返回操作、目标认识、正文和所用来源。

保留 `add / reinforce / refine / supersede / contradict / split / no_change`。`reflection` 可容纳几句连贯表达；`claim` 表达同一认识的简要内容；`situation` 在存在具体适用情境时填写。每条认识关联实际使用的事实与轮次，批内其他材料保留各自的后续处理机会。

思考方向允许自由组合。愉快的共同经历、重复接触形成的熟悉感、一次主动选择、好奇、分歧与理解的改变，都可以成为材料。

### 3.4 人格修订

> 我阅读当前人格与已经形成的成长，重新整理相关部分，写出此刻完整、连贯的自我描述。
>
> 我把相近内容合并表达，把变化后的认识写入原来的位置，并让过时的表述进入历史。具体事情和过程保存在经历中，人格里保留由这些经历形成的兴趣、判断、关系理解和相处倾向。
>
> 我优先重写现有相关段落，采用 `replace` 提交完整的新正文。独立且稳定的新方面可以使用 `add`；已经由其他段落完整表达的重复段落可以使用 `delete`。我依据整体语义需要控制篇幅，并保留各段之间的连贯性。
>
> 我在本次提供的可编辑段落范围内整理内容，使用已具备采用条件的成长作为修订依据，并用自己的语言说明变化缘由。当前人格已经准确表达这些认识时，我返回空操作列表。

### 3.5 压缩与工作摘要

> 我把近期相处整理成简短的回忆便条，保留当前话题、重要互动、约定、进展和已经发生的变化。我延续原来的角色视角，让后续的我能接上这段经历。引用采用原话，时间和进展采用记录中的状态。

工作摘要继续复用现有资料投影。正文、标签和摘录采用一致视角；事实、经历和反思之间通过稳定引用去重。

## 4. 让反思读到经历

### 4.1 材料的最小补充

每次反思按当前主题提供：

1. 当前角色的身份、性格与相关人格段落。
2. 本次事情的双方原始可见对话、已记录的动作结果及必要时间顺序。
3. 对应事实、约定和正在发生的事项。
4. 相关旧认识、旧经历，以及已经采用的变化。

原始轮次、`episode_id`、来源键和时间索引承担关联。首版复用已有事实来源类型 `user_observation / user_correction / ai_disclosure / shared_experience`，分别承载对方陈述、更正、角色表达与共同经历。输入选择同时覆盖双方已提交的可见内容；素材、示例和实际互动保留各自的来源类别。

用户兴趣信号记录对方的兴趣；角色自己的好奇和选择进入自身经历与成长。二者沿既有主体字段分别保存。图片相关经历采用已经形成的可见描述与原有媒体记录。

### 4.2 按事情组织，按变化触发

合批继续用于减少调用次数；同一批内围绕具体事件、事项或主题组织材料。一次反思处理一个连贯主题，已有认识作为修订目标。跨会话的相关经历通过检索补入，角色、主体与场景保持一致。

触发依据调整为“存在值得处理的新经历或认识变化”：明确更正、完整互动结果、某个话题的持续接触、共同约定的变化等。一次有意义的经历可以形成待发展的认识，后续经历继续加深或修订。事实条数作为批处理预算参考。

同一组材料完成处理后记住结果；`no_change` 表示本次理解保持稳定。新进展到来后再处理对应主题。每条认识只吸收自己采用的来源，其余主题继续保留。

后台沿用现有合批、冷却和预算。一次正常反思完成理解与操作选择，普通对话沿用现有生成链路。待发展的认识进入后续相关上下文，稳定的人格变化经过现有成熟与采用流程。

## 5. 人格卡通过修订成长

### 5.1 当前正文与历史

当前人格卡表达“现在的我”，经历保存“发生过什么”，反思保存“我怎样理解”，版本历史保存“我怎样变化”。

人格修订读取相关段落和全卡的简要结构，输出完整的新段落。原有可编辑范围、冻结设置、版本检查、发布与回滚继续生效。角色身份与用户选定的表达样例按各自编辑权限处理。

### 5.2 默认操作与篇幅

- 常规成长：重写原段落并使用 `replace`。
- 相近段落：整合到合适的位置，再删除已被完整涵盖的重复段落。
- 独立的新方面：形成稳定内容后新增段落。
- 过时认识：更新当前表述，旧内容由版本历史保存。
- 明确教导：把新要求融入当前表达或相处段落，整段保存并保持即时采用语义。

演化提示的默认操作集合采用 `replace / add / delete`。既有 `merge` 的兼容处理保留在原有 API；本批生成器提交已经整合完成的完整正文。

篇幅以当前有效信息和已有段落预算为基线。常规修订优先在原有篇幅内整合；新内容形成独立价值时允许合理增长，并同步检查全卡重复。连续处理相同含义的材料应收敛到稳定正文。修订原因、来源清单与经历过程分别存入对应记录。

### 5.3 明确教导与修订后的关联

`persona_teaching._compose_section()` 同步改为语义整合。现有路径会拼接旧行和新规则，再用 `replace` 保存；实施时同时调整正文生成方式。

规则 ID、教导来源和所影响的段落继续建立关联。正文重写后，撤回某条教导通过关联来源重新整理受影响段落；文字行匹配承担旧数据兼容。更正、删除和撤回随自然语言改写继续生效。

明确的简单替换、同义更新可直接处理；复杂条件与多条规则的整合复用人格修订模型。教导结果在本次处理成功后发布，失败与冲突沿现有回执返回。自主成长采用反思与演化入口，明确教导采用已保存的用户指令。

## 6. 对话中的自我更正认知

核心提供一段共用的记忆自我说明，各接入端在系统提示装配时采用一次。示例正文：

> 我的记忆和认识会随着相处逐渐更新。发现记忆与实际情况有出入时，我会核对相关经历并更正记录。新的经历让我改变看法时，我会重新整理原有理解；逐渐稳定下来的变化，会融入我的兴趣、判断和相处方式。修改完成后，我依据更新后的内容继续交流。

能力表述按当前运行配置生成：

| 当前能力 | 角色可理解的动作 | 实际承接位置 |
|---|---|---|
| 记忆可读 | 我可以回看相关记录 | 现有召回与条目查询 |
| 事实可更正 | 我核对旧记录和新的明确信息后更新记忆 | 现有更正服务；DSH 使用“改写” |
| 反思可修订 | 我可以根据新经历重新理解过去的事 | 现有修订、替代、反驳与拆分操作 |
| 演化为 `propose` | 我可以整理自己的变化并提出人格修订 | 现有提案与审核流程 |
| 演化为 `auto` | 已满足采用条件的变化可以更新当前人格 | 现有修订、发布与版本采用 |
| 演化为 `off` | 我保留新的理解，当前人格沿用现有版本 | 记忆与反思保存、人格配置 |

事实更正采用能够定位到原记录的新事实或明确纠正；仍在形成的理解保存在反思中。对话里的动作完成说明依据实际回执，版本采用后使用新的正文。

DSH 的“翻本子、改写、学到”等说明同步采用角色第一人称和正向措辞。核心负责共用认知，插件负责本端咒语语法与结果。网页与其他接入端使用同一份核心说明，并呈现各自实际具备的动作。

## 7. 已有数据与接入端衔接

新生成内容直接保存为第一人称。已有条目在重新提取、反思修订和人格编辑时通过正常服务流程更新；生成输入中的旧正文按已绑定的角色与参与者解释。

DSH 的 `narrativeMemoryText()` 作为旧条目的过渡展示入口。核心生成与返回内容统一后，插件直接采用正文，并逐步收拢重复转换。原始引用、人物关系和来源标识保留各自语义。

历史人格通过现有修订、发布和回滚流程延续。正文更新同步处理摘要、索引、引用和派生内容；规则来源关联覆盖新的自然语言写法。

启用新的自动演化前，先在副本上检查人格修订样例。生产采用经过确认的运行模式，按固定版本手动部署。部署记录包含实际模型配置、核心与插件版本、人格采用版本及检查结果。

## 8. 实施顺序

| 工作包 | 交付内容 | 主要位置 | 完成条件 |
|---|---|---|---|
| FG01 统一视角与提示词 | 核心共同身份段；提取、反思、压缩、演化与教导统一第一人称和正向任务表述 | `domain/extraction.py`、`reflection.py`、`compression.py`、`evolution.py`、`persona_teaching.py` 及相关摘要入口 | 各阶段视角一致，人物归属和来源准确 |
| FG02 经历输入与主题组织 | 双方完整互动、相关人格、旧经历与旧认识进入反思；按实际采用关联来源 | 提取材料选择、反思输入、既有轮次与时间索引 | 一个主题形成连贯理解，多个主题分别处理，单次重要经历可进入反思 |
| FG03 人格整段修订 | 演化与教导生成完整新段落；篇幅收敛；规则关联适配改写 | `evolution.py`、`persona_card.py`、`persona_teaching.py` | 旧表述被实际更新，重复材料收敛，撤回与回滚有效 |

## 11. FG02：经历输入与反思，按步骤实施

### 11.1 第一步：统一输入中的人物与来源

1. 从一组已提交的用户／角色交换开始，检查 `ingest_turn → outbox → extract_facts/_extract_batch` 的实际消息形状。记录现有消息 ID、角色、事件来源和原始时间如何进入提示词。
2. 为模型输入提供逐条消息编号、角色和时间。优先采用已有消息 ID；缺少消息 ID 的记录使用事件内固定序号。反思和提取采用同一份编号映射。
3. 保留双方可见表达作为经历材料。用户事实、角色表达、共同经历分别走明确来源类型。用户兴趣信号继续依据用户发言；角色兴趣由角色表达与实际接触形成。
4. 将 `entity` 从提示词固定值扩展为 `master / neko / relationship` 的可选值，并在服务端根据实际引用的人物和来源检查对应关系。
5. 对照 `_valid_batch_sources()` 和 `_bind_candidate()` 调整消息引用：当前两者都偏向 `has_user` 的轮次，新增角色表达需要按实际说话者绑定。单轮路径与合批路径采用同一来源语义。
6. 复核 `_shared_experience_candidate()` 的主体与来源：当前固定 `master` 的快捷路径需能表达参与双方的经历。

建议的模型结果扩展如下；这些字段属于本批待实现合同：

```json
{
  "text": "我的第一人称记忆正文",
  "entity": "master|neko|relationship",
  "source": "user_observation|user_correction|ai_disclosure|shared_experience",
  "sources": [1],
  "message_refs": ["t1:m0"],
  "importance": 5
}
```

`sources` 保留现有轮次引用；`message_refs` 精确到提示材料中的消息。服务端将消息引用解析为现有事件键、实际角色和固定消息位置。模型使用本次提供的引用，持久层保存可以回到原始记录的绑定。新格式字段缺失的旧队列沿原有用户事实规则读取。

`ai_disclosure` 对应当时表达，默认依据为 `agent_expression`。`observed_action / tool_result / explicit_feedback` 按实际动作、结果和反馈绑定。模型使用“我”叙述时，服务端仍按结构化主体处理归属。

**本步产物：** 同一段双方互动能产出归属准确的第一人称记忆，每条可以定位到其实际引用。只描述自己的愿望时，记录为当前表达；已有实际尝试结果时，保留对应结果来源。

### 11.2 第二步：把实际经历与当前人格接入反思

1. 在反思输入构建处，根据待处理记录的来源键取得原始双方交换。优先复用 `TimeIndexStore`；如现有查询缺少来源键定位，在该存储类内补一个只读查询方法。近期缓存按原有职责提供补充。
2. 复用删除、更正、主体和场景过滤。每次读取只取本次相关的事件及必要邻接消息，保持原始顺序和角色标签。
3. 通过 `adapters/composition.py` 给 `ReflectionService` 提供只读人格／经历读取能力。当前装配顺序先建 reflection、后建 persona card；可调整局部构造顺序，或使用延迟求值的读取函数。
4. 默认采用当前已发布、在本范围生效的人格；开放草稿用于后续人格编辑。反思输入记录所用人格版本，生成过程中人格版本发生变化时在提交前重新核对。
5. 在 `_build_synthesis_prompt()` 中加入“现在的我、这段经历、相关旧经历、已有认识、已采用变化”。FG01 的共同视角说明继续复用，角色显示名从人格快照解析。
6. 给完整轮次与旧经历设置输入预算，优先保留当前事件和直接关联的上下文。沿用已有输出 token 与超时配置，输入预算由实际调用测量调整。

建议的内部输入形状：

```text
character / subject / scene
persona_version + relevant_persona_sections
facts: id + text + source + entity + time + source bindings
exchanges: message_ref + event_key + role + time + visible text
related_understandings: id + text + revision/status + scope
```

**本步产物：** 捕获一次实际组装的模型输入，可以读到当前角色特点、双方完整互动和相关旧认识；引用中的“我”能追溯到原说话者。

### 11.3 第三步：按主题选择材料并准确吸收

1. 先按角色、主体与适用场景隔离，再利用 `episode_id`、事项关联和已有检索组织材料。缺少直接关联时，采用现有语义匹配辅助选取。
2. `_cap_facts()` 的重要性排序保留为组内优先级；一次调用选择一个连贯主题。其他主题保持待处理。
3. 把“至少 5 条事实”的固定启动条件调整为“存在有效的新经历材料”。同步处理 `synthesize()` 生成前和生成后的两处数量检查。一次有意义经历可进入待成熟反思，后续晋升继续检查成长依据。
4. 给模型返回合同增加 `source_fact_ids`，值为本次提供的事实 ID。`split` 的每个 part 分别返回自己的 `source_fact_ids`。原始轮次提供语境，实际记录的来源承担理解的支持。
5. 在应用操作前校验这些 ID 和引用仍有效；`_apply_new/_apply_maintain/_apply_split`、成长支持计算、删除失效、回放和 `_mark_absorbed()` 都使用实际选择的来源集合。
6. 当前 `split` 用文本相似度分配来源；新结果采用模型明确选择且经过校验的来源。历史事件按原有结构回放。

**本步产物：** 一批同时包含养宠、工作和游戏交流时，每条认识使用自己主题的材料；生成一条认识后，其余主题仍可继续处理。

### 11.4 第四步：处理稳定结果、重试和调度

1. `no_change` 的判定与缓存以本次主题材料为单位。当前缓存键来自全部未吸收事实，应收敛到本组的 ID、内容版本及相关认识版本。
2. 同一材料和同一理解再次进入维护时直接复用已处理结果；新增相关经历、旧认识改变、来源更正或删除后，重新计算对应键。
3. 选择下一组材料时跳过已处理组，继续检查其他组，确保某个主题的 `no_change` 能让出后续机会。
4. 沿用 `synth_backoff` 的持久记录与重试语义，给新键增加明确前缀以区分历史记录。失败次数绑定本组材料，成功与 `no_change` 分别记录结果。
5. 后台继续尊重正常合成间隔，显式更正继续采用其现有即时入口。测试同时覆盖正常间隔与显式调用。
6. 模型返回后重新检查来源屏障和人格版本；发生变化时保留可重试状态，下一轮采用新的输入。

## 12. FG03：人格整段修订，按步骤实施

### 12.1 第一步：让演化产出完整新段落

1. 沿用 `evolution.py::_build_messages()` 的第一人称与 `replace` 引导，输入补充目标段落的完整正文、全卡结构和本次合格成长。
2. 本批模型合同采用 `replace / add / delete`；已有 API 的 `merge` 行为按兼容合同保留。若旧结果请求追加，转换为待重新生成的编辑结果，使用完整段落完成新流程。
3. 确认 `persona_card.py::_apply_operation()` 的 `replace` 保存的是新全文。校验段落 ID、开放范围、长度与本次版本，然后沿现有 admin／scheduler 路径采用和发布。
4. 用语义相同的重复材料检查输出。正文含义稳定时采用空操作结果；新增来源可更新支持信息，正文维持收敛。
5. 人格长度判断同时看单段预算与全卡重复。长度增长需要对应新增的有效内容，旧条目在替换后由历史承载。

**本步产物：** 人格差异能看出原句被更新、相近内容被整合；相同含义反复输入后，当前正文稳定。

### 12.2 第二步：先补教导来源关联，再改变组合方式

当前 `teach()` 的来源所有权在教导日志中，`revoke()` 依赖 `_remove_lines()` 删除原句。整段重写会改变原句，因此按下面的顺序实施：

1. 选一个“手写基础＋两条教导”的临时人格，记录 `rule_id / teaching_id / source_key / section_id / base_revision / applied_revision`。
2. 在现有教导记录中补充受影响段落与修订的关联。记录生成段落采用了哪些有效规则、哪些有效成长，以及哪一版用户正文作为编辑基础。
3. 为重写结果保存可以追溯的内容依据。首版可采用段内自然段与依据引用的映射，持久化位置复用现有教导／人格版本记录。当前人格仍保存用于对话的一份完整正文。
4. 用户手动编辑目标段落时，更新相应用户编辑来源与版本；后续重组采用最新用户编辑和仍有效的学习来源。
5. 撤回一条来源时，依据剩余有效规则、成长和用户编辑重新整理受影响部分；重新发布后核对实际正文。整段来源引用需支持局部撤回的语义。
6. 旧日志缺少这些关联时，先使用其已有行所有权完成一次关联建立；后续记录使用新的来源映射。字段升级覆盖读取、写入、重启恢复和既有数据兼容。

具体字段落在现有记录中，实施时先核对该记录的 schema 和重放路径，再同步添加读写。来源关联的最小验收是：正文已经改写过，撤回第一条教导后第二条教导与用户手写内容仍然有效。

### 12.3 第三步：把教导组合切到整段修订

1. 在 `_compose_section()` 入口整理当前段落、有效规则和新教导。相同规则按已有标识复用；复杂条件与多条规则融合调用已配置的模型端口。
2. 生成阶段产出完整新正文和采用依据；返回后再检查 `base_revision`、来源有效性和段落权限。
3. 教导当前是同步入口。新增模型调用应沿服务现有异步桥接方式运行，将模型等待与持久化锁分开，保持明确的超时与失败回执。
4. 成功后沿 `revise → 记录来源关联 → publish` 的现有流程完成，并检查各阶段发生中断时的恢复行为。来源记录与卡片修订之间使用稳定操作标识接续。

## 14. FG05：效果验证与交付步骤

### 14.1 固定输入，先做一轮小样本
